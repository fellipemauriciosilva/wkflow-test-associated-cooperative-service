# Contexto do projeto

## Módulos

- `com.acme.votacao` — classe main (`VotacaoPautasApplication`).
- `com.acme.votacao.pauta` — pacote único, Fatias 1+2+3:
  - Fatia 1: `Pauta`/`PautaRepository`/`PautaRequest`/`PautaResponse`/`PautaIdResponse`/`PautaService`/`PautaController`/`PautaNaoEncontradaException`.
  - Fatia 2: `Sessao` (entidade JPA), `SessaoRepository`, `SessaoRequest`/`SessaoResponse` (DTOs), `SessaoService` (abertura com lock pessimista + isolamento fixado), `SessaoController` (`POST /pautas/{id}/sessao`), `SessaoJaAbertaException`, `ClockConfig` (bean `Clock.systemUTC()`), `GanchoConcorrenciaSessao`/`GanchoConcorrenciaSessaoNoOp`.
  - Fatia 3: `Voto` (entidade JPA, constraint `UNIQUE(pauta_id, associado_id)`), `VotoValor` (enum SIM/NAO), `VotoRepository`, `VotoRequest`/`VotoResponse` (DTOs), `VotoService` (orquestra 404 e normalização, delega 422/409/insert a `VotoTransacional`), `VotoTransacional` (`@Transactional` isolado, checagem de sessão + duplicado + insert atômicos), `VotoController` (`POST /pautas/{id}/votos`), `VotoDuplicadoException`, `SessaoNaoAbertaException`, `GanchoConcorrenciaVoto`/`GanchoConcorrenciaVotoNoOp` (barreira de teste, análoga à da Fatia 2); `StatusVotacao` (enum ABERTA/ENCERRADA/NAO_INICIADA), `ResultadoVotacaoResponse`, `ResultadoVotacaoService`, `ResultadoVotacaoController` (`GET /pautas/{id}/resultado`).
  - Compartilhado pelas três fatias: `ErroResponse` (corpo padronizado de erro) e `GlobalExceptionHandler`, cobrindo 400/404/409/422/415/405/406/404-de-rota/500. `GlobalExceptionHandler` estende `ResponseEntityExceptionHandler` (não é um `@RestControllerAdvice` solto com catch-all) — ver Decisões.
  - Só em teste: `DiagnosticoTestController` (`src/test`, pacote `com.acme.votacao.pauta`) — endpoint `GET /diagnostico?x=...` sem equivalente em produção, existe só para exercitar via HTTP real uma exceção do próprio Spring MVC (`MissingServletRequestParameterException`, parâmetro `@RequestParam` obrigatório ausente) que `GlobalExceptionHandler` precisa tratar sem virar 500. Detectado por component-scan porque está no mesmo pacote da aplicação; não adiciona rota nova a nenhum controller de produção.

## Stack e comandos

- Java 21, Spring Boot 3.3.4 (web, data-jpa, validation), H2 em memória, Maven.
- Build/teste: `mvnd test` (sem `clean`). Build isolado: `mvnd compile`.
- Rodar local: `mvnd spring-boot:run`. Com console H2: `mvnd spring-boot:run -Dspring-boot.run.profiles=dev`.
- H2: `jdbc:h2:mem:votacao`, `ddl-auto: update`, sem migração (Flyway não usado — fora de escopo para greenfield pequeno com H2 em memória).

## Convenções

- DTOs como `record` (Java 21), sem Lombok (não adicionado ao pom). Enums simples (`VotoValor`, `StatusVotacao`) sem lógica.
- Validação via Bean Validation (`@NotBlank`/`@Size(max=255)` em `PautaRequest`; `@Positive` + `@Max(1440)` em `SessaoRequest.duracaoMinutos`; `@NotBlank`/`@Size(max=255)`/`@NotNull` em `VotoRequest`). `GlobalExceptionHandler` trata dois grupos: (1) tudo que `ResponseEntityExceptionHandler` já sabe mapear para um `HttpStatusCode` (`MethodArgumentNotValidException`/`HttpMessageNotReadableException`/`TypeMismatchException`/etc., inclui valor de enum inválido em JSON, que vira `HttpMessageNotReadableException` → 400) via `handleExceptionInternal` sobrescrito, preservando o status original; (2) exceções próprias do domínio via `@ExceptionHandler` dedicado: `PautaNaoEncontradaException` → 404, `SessaoJaAbertaException`/`VotoDuplicadoException` → 409, `SessaoNaoAbertaException` → 422, `Exception` genérico → 500. Corpo de erro é `ErroResponse` (`timestamp`, `status`, `error`, `message`, `path`) para **todos** os handlers (RF-12).
- Handlers de 400 nunca usam `ex.getMessage()` bruto (ver Fatia 2). Status 5xx usa mensagem fixa; demais usam `status.getReasonPhrase()` como fallback.
- `Clock` é bean de produção (`ClockConfig`, `Clock.systemUTC()`), nunca `Instant.now()` direto em código de produção. `VotoTransacional`/`ResultadoVotacaoService` seguem o mesmo padrão de `SessaoService`.
- `spring.jackson.deserialization.accept-float-as-int: false` em `application.yml`: por padrão, o Jackson desserializa `3.5` em campo `int`/`Integer` truncando para `3` em vez de rejeitar — perigoso para campos como `duracaoMinutos`, onde um valor fracionário enviado por engano seria silenciosamente arredondado para baixo em vez de falhar com 400. Com a flag `false`, esse caso passa a lançar `InvalidFormatException` (→ `HttpMessageNotReadableException` → 400 pelo `GlobalExceptionHandler` existente).
- Pacote único `pauta` (sem camadas `api/application/domain/infrastructure`).
- Ordem de validação do voto (`VotoService.votar`, fixada no task.md): 400 (payload, via `@Valid` no controller, antes do serviço) → 404 (pauta, em `VotoService`) → 422 (sessão não aberta) → 409 (duplicado) — as duas últimas em `VotoTransacional.registrar`, na mesma transação do insert (ver Decisões, atomicidade). Checagem de duplicado é otimista (`existsByPautaIdAndAssociadoId`) **e** reforçada por confirmação após `catch (DataIntegrityViolationException)` no `save` — ver Decisões.
- `associadoId` é normalizado (`trim().toLowerCase(Locale.ROOT)`) em `VotoService.votar` antes de qualquer checagem e antes do `save` — `"associado-1"`, `"Associado-1"` e `" associado-1 "` contam como o mesmo associado para a constraint de unicidade. Decisão de normalização (não estava no task.md original; adicionada no ciclo 3 de correção).
- "Sessão aberta" para voto usa a mesma regra da Fatia 2 (`findFirstByPautaIdAndFimAfter`, `fim > agora` estrito — fronteira `agora == fim` é fechada). "Status da votação" (resultado) usa a **última** sessão da pauta (`findFirstByPautaIdOrderByFimDesc`), não "existe alguma aberta": `agora < fim` → ABERTA, senão ENCERRADA; sem nenhuma sessão → NAO_INICIADA.
- `UNIQUE (pauta_id, associado_id)` em `Voto` já cria, como efeito colateral, um índice com `pauta_id` como coluna líder — esse índice cobre tanto `existsByPautaIdAndAssociadoId` (usa as duas colunas, prefixo exato do índice) quanto `countByPautaIdAndVoto`/`countByPautaId` (usam só `pauta_id`, prefixo do índice). Um índice adicional em `voto.pauta_id` isolado seria redundante — não criar.

## Decisões

- (Fatia 2) `GlobalExceptionHandler` estende `ResponseEntityExceptionHandler` em vez de ser um `@RestControllerAdvice` com `@ExceptionHandler(Exception.class)` solto: um catch-all genérico intercepta exceções que o próprio Spring MVC já sabe mapear para 4xx (`HttpMediaTypeNotAcceptableException` → 406, `NoHandlerFoundException` → 404, `MissingServletRequestParameterException` → 400, etc.) e as converte em 500, porque `Exception.class` captura tipos mais específicos antes do framework decidir o status certo. Estender `ResponseEntityExceptionHandler` e sobrescrever `handleExceptionInternal` preserva o `HttpStatusCode` que o Spring já calculou, só trocando o corpo da resposta para o formato padronizado (`ErroResponse`). Provado por `DiagnosticoTestController` em teste (ver Módulos).
- (Fatia 2) Concorrência na abertura de sessão via lock pessimista + isolamento READ_COMMITTED fixado em `SessaoService.abrir` (`@Transactional(isolation = Isolation.READ_COMMITTED)` + `entityManager.find(Pauta.class, pautaId, LockModeType.PESSIMISTIC_WRITE)`): o lock pessimista na linha de `Pauta` serializa aberturas concorrentes para a mesma pauta — a segunda transação só adquire o lock após o commit da primeira. Mas isso só funcina se a leitura de `findFirstByPautaIdAndFimAfter` (que decide se já existe sessão aberta) ocorrer **depois** do lock ser adquirido, lendo o estado committed mais recente — em REPEATABLE READ/SERIALIZABLE (isolamento padrão de alguns bancos), o snapshot da transação é fixado no início dela, antes do lock, e a segunda transação não veria a sessão da primeira mesmo já commitada. Daí a necessidade de fixar READ_COMMITTED explicitamente, independente do default do datasource.
- (Fatia 3) Voto duplicado sob concorrência: duas camadas de defesa. (1) Checagem otimista em `VotoTransacional.registrar` (`existsByPautaIdAndAssociadoId`) evita round-trip ao banco no caminho feliz (99% dos casos não têm corrida). (2) A constraint `UNIQUE(pauta_id, associado_id)` do H2 é quem garante corretude sob concorrência real — se o `save` falhar por `DataIntegrityViolationException`, `VotoService.votar` confirma o duplicado com uma releitura de `existsByPautaIdAndAssociadoId` antes de converter em `VotoDuplicadoException` (409); se a releitura não confirmar, a exceção original é relançada (ver Armadilhas, mudança do ciclo 3). Diferente da Fatia 2 (lock pessimista, sem constraint de unicidade possível porque reabertura de sessão é permitida), aqui a dupla "pauta+associado" É sempre única — constraint de banco é a ferramenta certa, não lock.
- (Fatia 3, ciclo 3) Atomicidade entre checagem de sessão, checagem de duplicado e insert: extraídas para `VotoTransacional.registrar`, um `@Component` separado com `@Transactional(isolation = Isolation.READ_COMMITTED)` (mesmo padrão de `SessaoService.abrir`). Isso fecha a janela em que duas chamadas concorrentes (ou uma chamada e o relógio avançando além de `fim` no meio do processamento) veriam ambas "sessão aberta, sem voto prévio" antes de qualquer insert. `VotoTransacional` é um componente separado de `VotoService` de propósito: se o insert falhar por `DataIntegrityViolationException`, a transação já sofreu rollback nesse ponto — reconsultar o banco **dentro** da mesma transação que acabou de falhar no flush deixa a sessão do Hibernate em estado inválido (`HHH000099 AssertionFailure: null id ... don't flush the Session after an exception occurs`, reproduzido e investigado nesta sessão). Por isso a releitura de confirmação de duplicado, em `VotoService.votar`, roda fora da transação de `VotoTransacional` (nova transação, já com a anterior revertida).
- (Fatia 3) Prova de concorrência determinística para voto: `GanchoConcorrenciaVoto`/`GanchoConcorrenciaVotoNoOp` (ponto de extensão, chamado em `VotoTransacional.registrar` depois da checagem otimista e antes do `save`). Diferente do gancho de sessão (retém a 1ª thread indefinidamente até liberação explícita do teste), este é uma barreira simétrica de 2 partes (`CountDownLatch(2)`): ambas as chamadas concorrentes avançam até o `antesDeSalvar`, aguardam uma à outra, e só então os dois `save` disparam quase simultaneamente — é isso que exercita a constraint do banco de fato, não só a checagem otimista. Desarmado por padrão (`armado = false`, passa direto) via `ativarBarreira()`: como o bean é singleton por classe de teste, uma barreira sempre ativa bloquearia qualquer chamada de voto fora do próprio teste de concorrência.
- (Fatia 3) `NAO_INICIADA` (resultado de pauta sem sessão) e desambiguação sessão-inexistente-vs-pauta-inexistente (422 vs 404) implementados conforme task.md seção 4 — ambos marcados como "assumido, confirmar com PO" no próprio task.md; ver Pendências.
- (Fatia 3, ciclo 3) `associadoId` sem autenticação nem verificação de existência/elegibilidade é **risco aceito registrado formalmente** (não só mencionado no README): a constraint de unicidade só impede repetir exatamente a mesma string normalizada na mesma pauta; um cliente mal-intencionado pode votar múltiplas vezes trocando o `associadoId` a cada chamada. Decisão do PO (ciclo 3 de correção): manter fora de escopo nesta fatia, documentado aqui e no README como limitação conhecida, não como bug pendente de fix — mitigação real exigiria autenticação, que é explicitamente "fora" no task.md seção 2.

## Armadilhas

- (Fatia 2) `mvnd`/`mvn` resolvem via proxy interno — timeout/erro de download não é "rede quebrada", é artefato ausente no proxy.
- (Fatia 2) `@Size(max=255)` em DTO sem `@Column(length=255)` na entidade correspondente: o H2 usa o default da coluna (também 255 para `VARCHAR` sem tamanho explícito neste schema), mas a validação do DTO e o tamanho da coluna são coisas independentes — se um dia a coluna mudar, o DTO não acompanha automaticamente.
- (Fatia 2) Contaminação de teste entre métodos da mesma classe `@SpringBootTest` (dados de um teste visíveis no próximo, mesmo H2 em memória sem rollback automático entre métodos): usar `countByXxx` escopado (por pauta, por id), nunca `repository.count()` global nos asserts.
- (Fatia 2) Gancho de concorrência precisa estar depois do ponto de contenção real (lock, constraint) e antes do commit da transação — colocá-lo antes do lock/checagem não prova nada sobre concorrência real.
- (Fatia 2) Jackson trunca float para int por padrão ao desserializar campo inteiro — ver Convenções, `accept-float-as-int`.
- (Fatia 3) Mesma armadilha de contaminação entre métodos se repete em `VotoControllerTest`/`ResultadoVotacaoControllerTest`: `VotoRepository` ganhou `countByPautaId(Long)` só para isso, nunca usar `votoRepository.count()` em assert de "nenhum voto criado".
- (Fatia 3) Gancho de concorrência de voto (`GanchoConcorrenciaVotoControlavel`) **precisa** ser desarmável: diferente do gancho de sessão (um teste só, sempre libera no fim), aqui o mesmo bean singleton atende todos os métodos de `VotoControllerTest`; sem o `armado.set(false)` após a barreira passar e sem default "passa direto", qualquer chamada de voto em outro teste da mesma classe trava esperando uma segunda chamada que nunca chega.
- (Fatia 3) Valor de voto fora de SIM/NAO no JSON (ex. `"TALVEZ"`) falha na desserialização do enum *antes* do Bean Validation rodar — vira `HttpMessageNotReadableException`, já coberta pelo `handleExceptionInternal` existente (sem precisar de handler novo).
- (Fatia 3, ciclo 3) Reconsultar o banco (`existsByPautaIdAndAssociadoId`) **dentro** da mesma transação `@Transactional` que acabou de falhar no `save` por `DataIntegrityViolationException` quebra o Hibernate (`HHH000099 AssertionFailure: null id in ... entry (don't flush the Session after an exception occurs)`) — a sessão do Hibernate fica inválida após o flush falhar, mesmo que a exceção tenha sido capturada. Por isso a confirmação de duplicado precisa rodar numa transação separada (ou sem transação), nunca dentro do método `@Transactional` que fez o `save`. É por isso que `VotoTransacional` (transacional) e a confirmação pós-falha em `VotoService` (não transacional) são componentes separados — não um único método com `try/catch` interno.
- (Fatia 3, ciclo 3) `UNIQUE (pauta_id, associado_id)` já cobre, como índice, tanto a checagem de duplicado quanto a contagem por pauta — não adicionar índice extra isolado em `voto.pauta_id` (ver Convenções); o review anterior pediu esse índice por engano.
